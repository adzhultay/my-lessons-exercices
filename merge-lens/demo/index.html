Your merge conflict isn’t always a conflict.

Git merges JSON and YAML line by line. When a config file just gets its keys reordered — a regenerated lockfile, a reformatted manifest — and another branch made one real, unrelated change, Git still reports a conflict. Merge Lens compares by value instead of by line, so reordering produces no diff and no conflict. Genuine conflicts still show up, exactly as before.

How it decides

    
    
      
  • Unchanged on one side, changed on the other → the changed value wins.
    • 
      
  • Changed identically on both sides → no conflict.
    • 
      
  • Changed to different values on both sides → conflict, reported with the exact path and all three values.
    • 
      
  • Deleted on one side, unchanged on the other → the deletion wins.
    • 
      
  • Deleted on one side, modified on the other → conflict.
    • 
      
  • Lists of objects (e.g. Kubernetes containers, Compose services) are matched by name/id/key rather than position, so editing one entry never conflicts with an unrelated edit to another.
    • 
    

    

      What this doesn’t do: preserve YAML comments across a merge, guess array reordering without an identity field, or keep JSON’s exact original formatting. When a real conflict can’t be resolved structurally, it falls back to Git’s own merge-file conflict markers — never silent data loss.
